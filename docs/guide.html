1장

이 프로그램을 만든 목적

침해사고 분석에서 패킷이 중요한 이유

회사 PC 한 대가 랜섬웨어에 감염됐다고 해 봅시다. 대응 담당자가 가장 먼저 알아야 할 것은 세 가지입니다. 어디서 들어왔는지, 무엇을 했는지, 어디와 통신하고 있는지입니다.

PC 안의 로그는 공격자가 지울 수 있고, 백신은 이미 알려진 악성코드만 잡습니다. 반면 네트워크를 지나간 패킷은 공격자가 지울 수 없는 기록입니다. 방화벽이나 스위치에서 미리 떠 둔 패킷 캡처 파일(PCAP)이 있다면, 그 안에 접속한 사이트, 내려받은 파일, 외부 서버와 주고받은 신호가 모두 남아 있습니다.

용어
패킷
네트워크로 오가는 데이터의 최소 단위입니다. 편지 한 통에 비유하면 봉투(출발지·목적지 주소)와 내용물(데이터)로 이루어져 있습니다.
PCAP
패킷을 시간 순서대로 저장한 파일 형식입니다. Wireshark나 tcpdump로 만들며 확장자는 .pcap 또는 .pcapng입니다.
침해사고
공격자가 시스템에 무단으로 접근하거나 악성코드를 실행한 보안 사고입니다.

기존 방식의 어려움

패킷 분석에는 보통 Wireshark를 씁니다. Wireshark는 강력하지만 패킷을 보여 주는 도구이고, 무엇이 수상한지는 분석가가 직접 판단해야 합니다. 이번 실습 파일만 해도 패킷이 13,195개입니다. 입문자가 이 중에서 공격과 관련된 수십 개를 찾아내기는 쉽지 않습니다.

  • 어떤 필터를 걸어야 하는지 알려면 공격 유형을 먼저 알아야 합니다.
  • HTTP 응답이 gzip으로 압축되어 있거나 여러 패킷에 나뉘어 있으면 내용을 바로 읽을 수 없습니다.
  • 찾아낸 사실을 보고서로 정리하는 데에도 시간이 많이 걸립니다.

그래서 정한 설계 목표

이 프로그램은 Wireshark를 대신하려는 것이 아닙니다. "분석가가 어디부터 봐야 하는지"를 먼저 알려 주는 도구를 목표로 했습니다.

자동으로 찾아 준다

포트 스캔, 무차별 대입, 웹셸, 악성 파일 다운로드, C2 통신 같은 공격 흔적을 규칙으로 찾아 심각도 순으로 보여 줍니다.

근거를 함께 보여 준다

"위험합니다"에서 끝나지 않고, 어떤 패킷·URL·해시 때문인지와 MITRE ATT&CK 기법, 대응 권고를 같이 제시합니다.

설치 없이 실행된다

캡처 드라이버(Npcap)나 외부 라이브러리 없이 파일만 읽어 분석합니다. 압축을 풀면 바로 실행됩니다.

배우면서 쓸 수 있다

탐지 결과에서 세션, HTTP 원문, 패킷까지 따라 내려가며 "왜 이것이 공격인지"를 직접 확인할 수 있습니다.

2장

프로그램을 만들기 위한 계획

분석 도구를 만들 때는 화면부터 그리고 싶어지지만, 순서는 반대가 좋습니다. 데이터를 정확히 읽는 엔진을 먼저 만들고, 실제 샘플로 결과를 검증한 다음, 마지막에 화면과 배포를 붙였습니다.

기술 선택

항목선택이유
언어·플랫폼C# / .NET 8바이트 처리 성능이 좋고(Span<byte>), Windows 화면 개발(WPF)까지 한 언어로 할 수 있습니다.
화면WPF표(DataGrid) 수만 행도 가상화로 부드럽게 보여 주고, 데이터 바인딩으로 화면과 분석 로직을 분리하기 쉽습니다.
패킷 해석직접 구현SharpPcap 같은 라이브러리는 Npcap 설치가 필요합니다. 파일 형식과 프로토콜 구조를 직접 읽으면 설치가 필요 없고, 손상된 패킷도 끝까지 처리할 수 있습니다.
규칙 저장JSON 파일임계값과 웹 공격 패턴을 코드 수정 없이 바꿀 수 있습니다.
외부 탐지 엔진Suricata(선택)공개 룰셋 5만여 개로 알려진 악성코드를 이름까지 식별합니다. 자체 엔진과 서로 보완합니다.

단계별 진행

  1. 요구사항 정리

    "침해사고 분석에 필요한 질문"에서 출발해 기능을 뽑았습니다. 누가 공격했나(출발지), 무엇을 노렸나(서비스·계정), 무엇이 들어왔나(파일), 어디와 통신하나(C2).

  2. 읽기 엔진

    pcap/pcapng 파일 리더와 패킷 디코더(Ethernet → IPv4/IPv6 → TCP/UDP)를 만들고, 흩어진 TCP 패킷을 이어 붙이는 재조립 기능을 구현했습니다.

  3. 프로토콜 해석

    HTTP(분할 전송·gzip 해제), DNS, TLS 접속 도메인(SNI), FTP·메일·HTTP 로그인 정보를 해석했습니다.

  4. 탐지 규칙

    공격 유형마다 하나의 탐지기(Detector)를 만들고, 모두 같은 형식의 결과(심각도·근거·권고)를 내도록 통일했습니다.

  5. 명령줄 도구로 검증

    화면보다 먼저 CLI(pcapir)를 만들어 실제 샘플 3개를 반복 분석했습니다. 여기서 오탐과 버그를 가장 많이 찾았습니다.

  6. 화면(GUI)

    대시보드, 탐지 결과, 타임라인, 세션, HTTP, DNS, 파일, 패킷 탭을 만들고, 탐지 결과에서 관련 세션으로 바로 이동하도록 연결했습니다.

  7. 자동 테스트

    파서와 탐지 결과를 검사하는 테스트 44개를 작성했습니다. 규칙을 고쳐도 기존 탐지가 깨지지 않았는지 바로 확인할 수 있습니다.

  8. Suricata 연동과 배포

    Suricata 검사 결과를 탐지 결과에 합치고, 실행 파일 하나로 배포했습니다.

실제로 부딪힌 문제와 해결

계획대로만 진행되는 개발은 없습니다. 샘플로 검증하면서 발견한 문제들이 오히려 가장 좋은 공부거리였습니다.

발견한 문제원인해결
FTP 로그인 시도가 실제의 2배(1,398회)로 집계됨캡처 파일 안에 시각과 내용이 똑같은 패킷이 9,865개 중복 저장되어 있었습니다(파일 병합 흔적).패킷마다 시각과 해시를 비교해 중복 프레임을 제외하고 경고를 표시합니다. 결과는 703회로 바로잡혔습니다.
평범한 웹 서핑이 "호스트 스윕(정찰)"으로 탐지됨브라우저가 광고·CDN 서버 수십 곳에 접속하는 것을 스캔으로 오인했습니다.대상 대부분이 외부 서버이고 정상 응답했다면 스윕으로 보지 않도록 조건을 추가했습니다.
웹 글꼴 파일이 "암호화된 악성 페이로드"로 탐지됨EOT 글꼴은 압축되어 있어 엔트로피가 높지만, 파일 형식 판별 목록에 없었습니다.EOT·TrueType 글꼴의 매직 바이트를 추가했습니다.
캡처 중간부터 기록된 세션에서 계정 이름이 비어 있음USER 명령이 캡처 시작 전에 지나갔습니다.서버 응답 331 Password required for admin.에서 계정 이름을 추론합니다.
Suricata가 실행되자마자 종료됨Npcap이 WinPcap 호환 모드가 아니어서 wpcap.dll을 찾지 못했습니다.Suricata를 실행할 때 Npcap 폴더를 PATH에 자동으로 추가합니다.
배울 점

탐지 규칙은 실제 데이터로 검증하기 전까지는 가설일 뿐입니다. 오탐이 많은 도구는 분석가가 결국 경고를 무시하게 만듭니다. 그래서 고친 오탐 하나하나를 자동 테스트로 고정해, 다시 생기지 않도록 했습니다.

분석 파이프라인: 파일이 결과가 되기까지

파일을 열면 아래 순서로 처리됩니다. 앞 단계의 결과가 다음 단계의 재료가 되는 파이프라인 구조입니다.

Pcap파일 읽기파일 머리말로 형식을 판별하고, 패킷과 수신 시각을 하나씩 꺼냅니다.
Decoding패킷 해석바이트를 주소·포트·플래그 같은 의미 있는 값으로 바꿉니다.
Sessions세션 재조립같은 연결의 패킷을 묶고, 순서가 뒤바뀌거나 재전송된 조각을 정리해 이어 붙입니다.
Protocols프로토콜 해석이어 붙인 데이터에서 HTTP 요청, DNS 질의, 로그인 정보를 읽어 냅니다.
Analysis파일 추출·통계전송된 파일을 꺼내 해시를 계산하고, 프로토콜·IP별 통계를 냅니다.
Detection위협 탐지탐지 규칙을 차례로 적용하고, Suricata 경보가 있으면 합칩니다.
Analysis타임라인DNS·HTTP·탐지·파일 이벤트를 시간순으로 정렬합니다.
Reporting보고서화면 표시, HTML 보고서, CSV, 파일 저장으로 내보냅니다.

핵심 개념: TCP 재조립

웹 페이지 하나도 여러 패킷으로 쪼개져 전송되고, 네트워크 사정에 따라 순서가 뒤바뀌거나 같은 조각이 다시 오기도 합니다. TCP는 각 조각에 순서 번호(Seq)를 붙이므로, 이 번호로 정렬하고 겹치는 부분을 잘라 내면 원래 데이터를 복원할 수 있습니다.

// 도착 순서:  "World"(Seq 1007) → "Hello "(1001) → "Hello "(1001, 재전송) → "lo Wo"(1004, 겹침)
// 재조립 결과: "Hello World"   ← 테스트 코드로 검증하는 실제 예시
foreach (var seg in segments.OrderBy(s => s.Seq))
{
    if (seg.End <= expected) continue;        // 이미 받은 조각(재전송)은 건너뜀
    int skip = Math.Max(0, expected - seg.Start); // 겹친 앞부분은 잘라 냄
    output.Write(seg.Data, skip, seg.Length - skip);
    expected = seg.End;
}

확장 가능한 탐지 구조

모든 탐지 규칙은 같은 약속(인터페이스)을 따릅니다. 분석 결과를 받아 탐지 결과 목록을 돌려주기만 하면 됩니다. 새 공격 유형을 잡고 싶으면 이 약속을 따르는 클래스를 하나 추가하면 끝입니다.

public interface IDetector
{
    string Name { get; }
    IEnumerable<Finding> Detect(DetectionContext ctx);   // 심각도·근거·MITRE·권고를 담은 결과
}

판단 기준이 되는 숫자는 코드가 아니라 rules\settings.json에 있습니다. 예를 들어 "5분 안에 서로 다른 포트 15개 이상에 접속하면 포트 스캔"이라는 기준은 아래처럼 바꿀 수 있고, 화면의 규칙 다시 적용 버튼으로 바로 반영됩니다.

"PortScanMinPorts": 15,        // 서로 다른 포트 수
"PortScanWindowSeconds": 300,  // 시간 창(초)

① 대시보드에서 큰 그림 보기

분석은 1초 안에 끝나고, Suricata 검사까지 더해 약 6초가 걸립니다. 화면에서 읽어 낼 것은 세 가지입니다.

  • 판정: 심각 등급 탐지가 4건 있습니다. 단순한 의심이 아니라 감염 정황이 있다는 뜻입니다.
  • 트래픽 그래프: 17시 58분 무렵에 큰 봉우리가 몰려 있습니다. 이 시간대를 집중해서 봐야 합니다.
  • 상위 통신 IP: 192.168.137.239가 가장 많이 통신했습니다. 사설 IP(192.168.x.x)이므로 이것이 내부 PC, 즉 조사 대상입니다.

② 탐지 결과에서 위험 신호 확인

가장 눈에 띄는 것은 자체 엔진이 찾은 심각 익스플로잇 킷 감염 체인입니다. 오른쪽 근거를 읽으면 다음 흐름이 보입니다.

  1. 사용자는 정상 사이트 vitaminsthatrock.com에 접속했습니다(Referer 기록).
  2. 그 직후 낯선 도메인 vclphjybj.ioxbpjgtqvwqfzmwhn.ga의 13390번 포트로 이동했습니다. 무작위 문자열 도메인, 흔치 않은 포트는 전형적인 악성 서버의 특징입니다.
  3. 그곳에서 Flash 파일(SWF)과 307 KB짜리 파일을 내려받았습니다. 이 파일은 이름이 .html인데 내용은 HTML이 아니고, 엔트로피가 8.00(최댓값)이라 암호화된 데이터입니다.
용어
익스플로잇 킷
방문자 브라우저의 취약점(여기서는 Flash)을 자동으로 공격해 악성코드를 설치하는 공격 도구 모음입니다. 정상 사이트를 해킹해 방문자를 킷으로 몰래 보냅니다.
엔트로피
데이터가 얼마나 무작위한지를 0~8로 나타낸 값입니다. 일반 문서는 4~5 정도이고, 암호화되거나 압축된 데이터는 8에 가깝습니다. 악성코드는 탐지를 피하려고 자신을 암호화해서 전달합니다.

③ IDS 경보로 위협의 이름 확인

Suricata 검사를 누르면 공개 룰셋으로 같은 파일을 한 번 더 검사합니다. 자체 엔진은 "익스플로잇 킷으로 무언가가 설치됐다"까지 알려 주지만, Suricata는 그 무언가의 이름을 알려 줍니다.

  • ET EXPLOIT_KIT Possible Evil Redirector Leading to EK: 정상 사이트(64.20.39.203)의 응답에 익스플로잇 킷으로 보내는 코드가 심어져 있었습니다. 최초 유입 지점입니다.
  • ET MALWARE AlphaCrypt CnC Beacon, Alphacrypt/TeslaCrypt Ransomware CnC Beacon Response: 내부 PC가 72.55.148.19와 랜섬웨어 C2 통신을 했습니다. 설치된 것이 랜섬웨어였다는 결정적 증거입니다.

모든 경보는 분석기의 세션 번호와 연결되어 있어, 세션 보기로 실제 대화 내용을 바로 확인할 수 있습니다.

④ 근거를 원문으로 확인: HTTP와 세션

검색창에 13390을 입력하면 악성 서버와의 요청 4건만 남습니다. 응답 본문에는 의미 없는 이름의 변수(ucnojasxgkcgrtya = 794340)와 Flash를 실행하는 <object> 태그가 있습니다. 사람이 읽지 못하도록 일부러 뒤섞은 난독화의 흔적입니다. 요청의 Referer 헤더가 http://vitaminsthatrock.com/이므로, 이 페이지로 보낸 곳이 해킹된 정상 사이트임을 다시 확인할 수 있습니다.

세션 탭에서 72.55.148.19를 검색하면 C2 통신 2건이 나옵니다. PC는 WordPress 플러그인 경로처럼 보이는 주소(/wp-content/plugins/…/misc.php)에 긴 16진수 문자열을 붙여 보냈습니다. 감염 정보를 암호화해 전달한 것으로 보입니다. 서버는 ---!!!INSERTED!!!---라고 짧게 답했는데, 감염 PC 등록을 확인하는 응답으로 추정됩니다. 정상 웹 서핑에서는 볼 수 없는 형태입니다.

세션에서 이 세션의 패킷 보기를 누르면 연결 하나가 패킷 13개로 어떻게 이루어졌는지 보입니다. 맨 위 세 줄 [SYN] → [SYN, ACK] → [ACK]는 TCP 연결을 맺는 3-way 핸드셰이크이고, 이어서 HTTP 요청(#10483)과 응답이 오가며, FIN·RST로 연결이 끝납니다. 보고서에 "프레임 #10483"처럼 패킷 번호를 적어 두면 다른 분석가도 같은 증거를 찾을 수 있습니다.

지금까지 찾은 조각을 시간순으로 놓으면 공격의 전체 흐름이 됩니다. 아래는 이 사례의 실제 시각(UTC)입니다.

  1. 17:58:16.021정상 사이트 방문 HTTP사용자가 vitaminsthatrock.com(64.20.39.203)에 접속합니다. 이 사이트는 해킹되어 있었습니다.
  2. 17:58:18.629익스플로잇 킷으로 유도 Suricata응답에 심어진 코드가 브라우저를 악성 서버로 보냅니다. (ET EXPLOIT_KIT Possible Evil Redirector)

핵심

정상 사이트에 접속한 지 약 17초 만에 랜섬웨어가 C2 서버에 감염 사실을 보고했습니다. 트래픽만 보면 사용자가 한 일은 사이트 하나를 연 것뿐입니다. 방문만으로 감염되는 이런 공격을 드라이브 바이 다운로드라고 합니다. 브라우저 플러그인(Flash, Java)을 최신으로 유지하거나 없애는 것이 왜 중요한지 보여 주는 사례입니다.

⑥ 증거 확보: 추출 파일과 정상 잡음 구분

프로그램은 전송된 파일 212개를 모두 꺼내 해시를 계산합니다. 파일 이름이나 서버가 알려 준 형식(Content-Type)은 속일 수 있으므로, 파일 맨 앞의 매직 바이트로 실제 형식을 판별합니다. SHA256 해시를 VirusTotal 같은 위협 정보 서비스에서 검색하면 이 파일이 이미 알려진 악성코드인지 확인할 수 있습니다.

모든 트래픽이 수상한 것은 아닙니다. DNS 탭을 열면 teredo.ipv6.microsoft.com, isatap.mshome.net 같은 질의가 "존재하지 않는 도메인(NXDOMAIN)" 응답과 함께 수십 번 나옵니다. 이것은 Windows가 IPv6 기능을 찾느라 보내는 정상 잡음입니다. 입문자가 가장 많이 하는 실수가 이런 잡음을 공격으로 오해하는 것입니다. 이 프로그램은 잘 알려진 정상 도메인을 DnsAllowList로 제외해 오탐을 줄입니다.

감염된 내부 PC의 IP 주소는 무엇이고, 어떻게 알 수 있나요?

192.168.137.239입니다. 대시보드의 상위 통신 IP 1위이고, 사설 대역(192.168.x.x)이며, 모든 심각 탐지의 대상(또는 출발지)이 이 주소입니다.

사용자가 처음 접속한, 해킹된 정상 사이트는 어디인가요?

vitaminsthatrock.com(64.20.39.203)입니다. 랜딩 페이지 요청의 Referer 헤더와 Suricata의 ET EXPLOIT_KIT Possible Evil Redirector 경보가 이 사이트를 가리킵니다.

307 KB 페이로드는 왜 HTML이 아니라고 판단할 수 있나요?

파일 이름은 …-handle-none.html이지만 서버가 알려 준 형식은 application/octet-stream이고, 매직 바이트로 판별되는 형식이 없으며, 엔트로피가 8.00으로 최댓값입니다. 텍스트인 HTML은 엔트로피가 이렇게 높을 수 없으므로 암호화된 바이너리입니다.

악성코드가 C2 서버보다 먼저 ipinfo.io에 접속한 이유는 무엇일까요?

감염 PC의 공인 IP 주소를 알아내기 위해서입니다. 랜섬웨어는 피해자의 위치나 네트워크 정보를 C2 서버에 함께 보고하는 경우가 많습니다. 정상 프로그램은 이런 서비스를 거의 쓰지 않으므로 감염 직후의 좋은 단서가 됩니다.

다른 PC를 조사하기 위한 IOC 목록을 만들어 보세요.

아래 내용을 텍스트 파일로 저장하고 IOC 불러오기로 다른 캡처를 검사할 수 있습니다.

46.108.156.181            # 익스플로잇 킷 서버
ioxbpjgtqvwqfzmwhn[.]ga   # 익스플로잇 킷 도메인(하위 도메인 포함)
72.55.148.19              # 랜섬웨어 C2
asecproteccion[.]com      # 랜섬웨어 C2 도메인
a5ef5b9fdae4f9c6edafd1b2ea6a6a67cdee4cee793841917996e3501b8adacc  # Flash 익스플로잇 SHA256
387d6f4670bfd929e4b91fc715cb03c86ddf926dc9c39d783181467224b6edf9  # 암호화 페이로드 SHA256

침해된 정상 사이트(64.20.39.203)는 차단보다 모니터링 대상으로 두는 것이 일반적입니다. 사이트 자체는 피해자이고, 운영자가 복구하면 다시 정상이 되기 때문입니다.

DNS 탭의 teredo.ipv6.microsoft.com NXDOMAIN 수십 건은 DGA 공격일까요?

아닙니다. 같은 이름을 반복해서 질의하는 Windows의 IPv6 전환 기능(Teredo)입니다. DGA는 매번 서로 다른 무작위 도메인을 질의하는 것이 특징입니다. 질의 이름이 다양한지, 같은지를 먼저 확인하세요.

용어 정리

세션
두 컴퓨터 사이의 연결 하나. 출발지 IP·포트와 목적지 IP·포트(5-tuple)로 구분합니다.
3-way 핸드셰이크
TCP 연결을 맺는 과정. SYN → SYN/ACK → ACK 세 번의 신호를 주고받습니다.
C2 (Command & Control)
공격자가 감염된 PC에 명령을 내리고 정보를 받는 서버입니다.
비컨
악성코드가 C2 서버에 "살아 있다"고 주기적으로 보내는 신호입니다.
IOC
침해 지표(Indicator of Compromise). 악성 IP, 도메인, 파일 해시처럼 공격을 식별하는 단서입니다.
IDS
침입 탐지 시스템. Suricata, Snort가 대표적이며 알려진 공격 패턴(룰)과 트래픽을 비교합니다.
MITRE ATT&CK
실제 공격 기법을 체계적으로 정리한 공개 지식 베이스. T1189(드라이브 바이 감염)처럼 번호로 부릅니다.
매직 바이트
파일 맨 앞에 있는 형식 표시. 실행 파일은 MZ, PDF는 %PDF, 압축된 Flash는 CWS로 시작합니다.
해시(SHA256)
파일 내용으로 계산한 고유한 값. 한 바이트만 달라도 완전히 바뀌므로 파일을 식별하는 지문으로 씁니다.
난독화
코드를 사람이 읽기 어렵게 일부러 뒤섞는 기법. 악성 스크립트가 분석과 탐지를 피하려고 사용합니다.
UTC
세계 표준시. 이 프로그램의 모든 시각은 UTC이며, 한국 시간은 UTC에 9시간을 더하면 됩니다.
